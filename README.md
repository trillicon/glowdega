# glowdega

GLOWDEGA® Gazette — static archive on Cloudflare Pages, plus an admin for reviewing and publishing new posts.

## Layout

| Path | What it is |
|---|---|
| `index.html`, `blog.html`, `blog/*.html`, `404.html` | Static archive, generated by `tools/build.py` from the Squarespace export |
| `assets/posts.json`, `assets/templates/article.html` | Archive index and article template used by the functions |
| `functions/` | Pages Functions: new posts at `/blog/<slug>`, home/archive merging, admin API |
| `admin/` | Review queue UI at `/admin` |
| `migrations/` | D1 schema |
| `_redirects`, `_routes.json` | Old URL redirects; which paths run functions |
| `/sitemap.xml`, `/robots.txt` | Generated by functions; include posts published from the admin |

Rebuild the archive: `python3 -I tools/build.py <export.xml> .`, then check it: `python3 -I tools/check_site.py .`
Function tests: `node --test tests/*.test.mjs`

- **Photos (`/admin/#images`):** uploads go to the R2 bucket `glowdega-images` (Pages binding `IMAGES`) and are public at
  `https://images.glowdega.com/<folder>/<name>`. Production sets `IMAGES_PREFIX=posts/`; previews leave it unset and write
  to `preview/`, so test uploads never land in the real folder. File type is checked from the file's bytes (JPG, PNG, WebP,
  GIF; 10 MB max), names are cleaned, and an existing name gets `-2`, `-3`… instead of being overwritten. The archive's own
  images are mirrored under `img/` and are not editable from the admin.

- **Home page order:** most-searched first, from `tools/popularity.csv`, the Search Console export
  (Performance → Pages → Export → CSV; use `Pages.csv` from the zip). The CSV is git-ignored (the repo is public);
  only the ranked slugs are published, in `assets/popular.json`, and later builds reuse that ranking when the CSV is absent.
- **Ads (`/admin/#ads`):** see [Ads](#ads) below.
- **Fonts:** self-hosted in `assets/fonts` (Bricolage Grotesque for titles, Spectral Light for text; OFL).

## Publishing flow

1. A draft is submitted to `POST /api/drafts` (AI tools use this).
2. It appears under **Drafts** at `/admin`. Edit it, open **Preview** to see it in the site design.
3. **Approve & publish now** puts it live at `/blog/<slug>` and on the home and Gazette pages immediately.
   **Schedule** publishes it automatically at the chosen time. **Reject** keeps it out with a note.
4. **Unpublish** takes a live or scheduled post back to draft.

Nothing reaches the public site without an approval in `/admin`.

### Submitting a draft

```sh
curl -X POST https://<site>/api/drafts \
  -H "Authorization: Bearer $DRAFTS_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"title":"…","body_md":"Markdown body…","category":"Acne","excerpt":"optional","hero_image":"https://…","source":"claude"}'
```

Returns `201 {"id","slug","status":"draft","review_url"}`. `slug` is optional (derived from the title).
A `## FAQ` section with `### Question` headings becomes FAQPage structured data; every article also gets
BlogPosting markup with Hadiyah as author.
Markdown only: raw HTML in a draft is shown as text, and only `https:`, `mailto:` and site-relative links are kept.

## Ads

Manage them in `/admin/#ads`: upload the image (JPG, PNG, WebP or GIF, 10 MB max; stored in R2 under `ads/` and never
overwritten), name it, give the https:// link, alt text and size, then pick where it runs:

- **Sizes:** `rail` 300 × 600 in the right column of every article; `inline` 728 × 90 between the photo/details and the text.
- **Targets:** tick categories and tags in the searchable list (post counts shown). An ad runs on articles that have any
  of them. Archive articles carry their category and tag slugs in `<article data-ad-terms="…">` (written by
  `tools/build.py`); posts published from the admin are targeted by their category.
- **Default ad** runs on articles that no active ad targets. With several defaults (or several matching ads) one is
  picked at random on each page view.
- **Schedule:** optional start and end dates (the end date is the last day shown). Pause/Resume stops or restarts it at once.
- **Choosing per slot:** active, in-date ads of that size matching the page → random one; else an active, in-date default
  of that size → random one; else the rail shows the placeholder and the inline slot is left out.
- **Stats:** every rendered ad counts a view; clicks go through `/go/ad/<id>`, which counts and redirects (unknown, paused
  or ended ads redirect to the home page). Article pages are filled per request, so they are served `no-store`.

Code: `functions/_lib/ads.js` (choosing, markup, validation), `functions/blog/[slug].js` (fills archive pages with
HTMLRewriter, admin posts via `articlePage`), `functions/api/admin/ads/`, `functions/go/ad/[id].js`, `admin/ads.js`,
table in `migrations/0003_ads.sql`. Tests: `tests/ads.test.mjs` (the HTMLRewriter test runs in the miniflare bundled
with wrangler).

## Configuration (Cloudflare Pages → Settings)

| Name | Type | Purpose |
|---|---|---|
| `DB` | D1 binding | Posts database (separate databases for Preview and Production) |
| `DRAFTS_TOKEN` | Secret | Bearer token for `/api/drafts` (64 hex chars) |
| `ACCESS_TEAM_DOMAIN` | Variable | `https://<team>.cloudflareaccess.com` |
| `ACCESS_AUD` | Variable | Access application audience tag |
| `ADMIN_EMAILS` | Variable | Optional allow-list of admin emails |

`/admin` and `/api/admin/*` must be protected by a Cloudflare Access application; the functions also verify the
Access token themselves and refuse all admin requests when Access isn't configured.

## Local development

```sh
printf 'ADMIN_DEV_BYPASS=true\nDRAFTS_TOKEN=%s\n' "$(openssl rand -hex 32)" > .dev.vars
wrangler pages dev . --d1 DB=00000000-0000-0000-0000-000000000000 --persist-to .wrangler/state
```
Apply `migrations/` to the local database first with `wrangler d1 migrations apply … --local`.
`ADMIN_DEV_BYPASS` only works on localhost.
